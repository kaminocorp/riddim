## 1. What Riddim is, and what it isn't

**It is:**
- **Our own native audio engine, written in Rust, in its own repo.** It covers device I/O, the transport and tempo map, tracks and clips, the mixer graph, automation, recording, plugin hosting (AU, VST3, later CLAP), metering and offline render.
- **The engine behind Whiplash.** Whiplash is its first client, and talks to it through one defined API (§1.1). Later clients, all secondary, could be an automation or agent layer, a headless renderer (CLI or server), and test harnesses.
- **macOS first.** That means CoreAudio and Apple Silicon (arm64). Windows comes later, and the plan keeps it reachable without building for it now.
- **Built from the best ideas, not from anyone's code.** We read Tracktion Engine, JUCE, Ardour and the Rust audio projects (§2) and take their approaches freely. We don't paste their code. All Riddim code is ours, which is what keeps the licence strategy in §6 open.

**It isn't:**
- **A fork, a clone or a wrapper** of Tracktion, JUCE, Ardour or any other engine.
- **A UI toolkit or a DAW.** It draws nothing except the native windows that host plugin editors. Arrange views, editors, the browser and undo UX all belong to Whiplash.
- **A plugin framework.** It *hosts* plugins. [nih-plug](https://github.com/robbert-vdh/nih-plug) is for writing plugins, and that's a different problem.
- **A general game or app audio library.** [Firewheel](https://github.com/BillyDM/Firewheel) covers that, and its own design doc explains why game and DAW engines diverge (§2.4).

### 1.1 The boundary with Whiplash

The rule: **Riddim owns everything that has to be correct in time** (samples, latency, plugin lifetimes, files being written). **Whiplash owns everything about intent and presentation.**

| Riddim (engine) | Whiplash (app) |
|---|---|
| Audio and MIDI devices, sample rate, buffer size, audio workgroups | The device-picker UI and preferences |
| **The engine model**: tracks, clips, routing (buses, sends, inserts), automation curves, tempo/meter map, and plugin slots with opaque state. These are typed, serialisable, versioned Rust data (`riddim-model`) | The **project**: the folder layout, the file format wrapping the engine model, the media pool, UI state (zoom, selection, colours, window layout) |
| **Edit operations** (`Op`) that are validated and applied atomically. Each one returns its **inverse op** | The **undo stack**: grouping ops into user-level commands, merging drags, labels. Undo stays simple because every op returns its inverse |
| Transport, the playhead, loop and punch, metronome, count-in | Transport controls and display |
| Graph compilation, PDC, real-time rendering, offline bounce | Bounce dialogs and stem selection |
| Plugin scanning (out of process), instantiation, parameters, state blobs, latency, editor windows | The plugin browser, favourites, quick-control mappings, window placement policy |
| Recording: capture, latency-corrected placement, writing files incrementally | Arming UX, take management and naming |
| Meters, CPU and disk load, xrun and overflow events | Meter drawing, warnings |

**API shape:** three channels, all non-blocking from the caller's side.
- **Commands** (`apply(ops)`, `transport(cmd)`, `set_param(...)`). They are applied on the engine's control side and acknowledged with a revision number.
- **Queries**: snapshot reads of the model and of engine state.
- **Events**: a subscription stream for playhead position, meters, parameter changes from plugin GUIs, latency changes, recording progress, xruns, plugin crashes and scan results.

The native API is a Rust crate (`riddim`). A **C ABI** (`riddim-ffi`, with headers generated by cbindgen) keeps a Swift or AppKit Whiplash front end possible, along with other languages later. Whiplash's UI stack is still open (Q2), so the ABI must not assume Rust on the other side.

**Why the engine owns the model types but not undo or the project file:** the engine has to validate every edit against the live graph. A send can't create a cycle, and a plugin slot has to exist. So the engine must be the one that knows the shape. Undo semantics and the file format are product decisions, and they change faster than the engine. The Whiplash vision makes the same call ("the project model is separate from the audio engine", its §5), and an agent layer later gets the same op API the UI uses.

### 2.1 By concern

| Concern | Tracktion Engine | JUCE | Ardour / libardour |
|---|---|---|---|
| **Graph and parallelism** | Each `Node` reports its own latency. `LockFreeMultiThreadedNodePlayer` processes ready nodes from a lock-free FIFO, with an atomic count of pending inputs per node. Its thread-pool strategy is pluggable (real-time spin, semaphore, hybrid). See `tracktion_graph/tracktion_graph/tracktion_Node.h`, `tracktion_NodePlayerThreadPools.h` and the design write-ups in `tracktion_graph/docs/` | `AudioProcessorGraph` is **single-threaded**. A `RenderSequence` is built off the audio thread, swapped in with a try-lock at the top of the callback, and the old one is freed by a timer (`juce_audio_processors_headless/processors/juce_AudioProcessorGraph.cpp`) | `Graph` has a main thread plus N helpers, an MPMC trigger queue and semaphores. Its nodes are whole routes (`ardour/graph.cc`, `ardour/ardour/graph.h`) |
| **Transport, clock, tempo** | `TransportControl` state lives in a ValueTree, and `TempoSequence` is read through `tempo::Sequence` (`tracktion_engine/playback/tracktion_TransportControl.h`, `model/edit/tracktion_TempoSequence.h`) | None. JUCE only relays the host's `AudioPlayHead::PositionInfo` | `TransportFSM` is an explicit state machine (`ardour/ardour/transport_fsm.h`). Time is **integer `superclock_t`** (`temporal/temporal/superclock.h`). The `TempoMap` is RCU-managed, and each thread reads its own snapshot (`temporal/temporal/tempo.h`) |
| **Edit / session model** | `Edit` is a `juce::ValueTree` plus an `UndoManager` (`model/edit/tracktion_Edit.h`), saved as XML or a binary stream (`tracktion_EditFileOperations.cpp`) | Building blocks only (`ValueTree`, `AudioProcessorValueTreeState`) | `Session` is an XML `.ardour` file plus a `.pending` capture-recovery file and a `.history` undo file (`ardour/filename_extensions.cc`). Each `Route` holds a `ProcessorList` (`ardour/ardour/route.h`) |
| **Plugin hosting** | Through JUCE: `ExternalPlugin` wraps `AudioPluginInstance` (`plugins/external/tracktion_ExternalPlugin.h`). Scanning runs out of process (`plugins/tracktion_PluginScanHelpers.h`) | `AudioPluginFormatManager`, plus VST3, AU and LV2 formats (`juce_audio_processors/format_types/`). A "dead man's pedal" file blocklists plugins that crash the scanner (`scanning/juce_PluginDirectoryScanner.h`). Out-of-process scanning exists only in sample code (`extras/AudioPluginHost/.../MainHostWindow.cpp`). **No CLAP hosting** | Native, in `ardour/vst3_plugin.cc`, `audio_unit.cc` and `lv2_plugin.cc`. Separate scanner executables (`fst/vst3-scanner.cc`, `auscan/au-scanner.cc`). **In process by design** (§4.4) |
| **Recording** | `WaveInputDevice` queues blocks to a `WaveInputRecordingThread`. That queue takes `CriticalSection` locks and can allocate (`playback/devices/tracktion_WaveInputDevice.cpp`) **[a pattern we avoid]** | `AudioFormatWriter::ThreadedWriter`: a FIFO feeding a `TimeSliceThread` | `DiskWriter` writes into pre-sized ring buffers, and the **Butler** thread flushes them to disk; the audio thread wakes it through a cross-thread channel (`ardour/ardour/butler.h`, `disk_writer.cc`) |
| **PDC** | Local: a `SummingNode` inserts a `LatencyNode` on each shorter input (`tracktion_graph/nodes/tracktion_SummingNode.h`). `PluginNode` shifts automation by the plugin's latency | The graph builder adds a delay op to each shorter input | Global: `Session::update_latency_compensation` walks all routes, and capture alignment uses capture and playback offsets (`disk_writer.cc`) |
| **Threading, UI↔audio** | Any edit triggers `restartPlayback()`, which **rebuilds the whole node graph** on the message thread and hands it over (`playback/tracktion_EditPlaybackContext.cpp`) | Message thread plus audio thread, with sequence swap | Read-copy-update (RCU): the audio thread reads a snapshot, writers copy, modify and publish, and old copies are reclaimed later (`pbd/pbd/rcu.h`). The UI sends commands as `SessionEvent`s from per-thread pools. Some try-locks remain in `process()` |

### 2.2 Others worth learning from

- **Zrythm** ([repo](https://github.com/zrythm/zrythm)) is now C++23 with Qt/QML and JUCE, under AGPL-3.0-or-later with trademark terms.
  - It hosts CLAP, VST3, LV2 and AU, and has an out-of-process scanner.
  - Its `src/dsp/graph_scheduler.h` carries an Ardour copyright line, so it is an Ardour-derived scheduler.
  - It moved from Carla to JUCE hosting, then replaced JUCE's VST3 hosting with native code in v2 alpha.3 ([releases](https://github.com/zrythm/zrythm/releases)). That is a data point that owning the format layer pays off.
- **Meadowlark** (Rust DAW, AGPL, [Codeberg](https://codeberg.org/Meadowlark/Meadowlark), dormant). Its [design doc](https://github.com/MeadowlarkDAW/Meadowlark/blob/dev-(old)/DESIGN_DOC.md) planned CLAP first, f32-only graphs and no JUCE.
  - **Its author's post-mortem** ([blog, 2023-04-14](https://billydm.github.io/blog/why-im-taking-a-break-from-meadowlark)) is the most useful thing here. The MVP scope was too large, building started before the architecture was written, there were too many crates, and the GUI toolkit was far harder than expected.
  - Riddim answers each: one client and four plugins, this doc first, a small crate set, and no UI.
- **Firewheel** ([repo](https://github.com/BillyDM/Firewheel), v0.15.0, 2026-11-13, MIT/Apache-2.0). This is the same author's current graph engine, aimed at games and Bevy. It is single-threaded on purpose.
  - Its `DESIGN_DOC.md` names the DAW difference: **in a DAW the transport and automation own parameter state, so conflicting user events may be dropped.** A game must deliver every event.
- **Carla** ([repo](https://github.com/falkTX/Carla), GPL-2.0+). The reference design for **plugin bridging**, in `source/utils/`: a shared-memory audio pool, semaphores to wake the bridge, and separate real-time and non-real-time opcode rings (`CarlaShmUtils.hpp`, `CarlaRingBuffer.hpp`, `CarlaBridgeDefines.hpp`). It is GPL, so we read it and don't link it.

### 2.3 What we take, and what we avoid

| From | Take | Avoid |
|---|---|---|
| **Tracktion** | Latency-reporting nodes, with delay inserted where paths sum. A lock-free multithreaded player with a pluggable wait strategy. The same graph for real-time and offline render | Rebuilding the whole graph on every edit. A recording queue that locks and allocates |
| **JUCE** | Compile the render plan off-thread, swap it in without blocking, free the old one off-thread. The scanner's crash blocklist | A single-threaded graph. No tempo or session model |
| **Ardour** | RCU-style snapshots for everything the audio thread reads. **Integer superclock time.** Butler-style disk threads with pre-sized buffers. An explicit transport state machine. Separate scanner executables | Try-locks scattered through `process()`. Twenty years of special cases |
| **Zrythm** | An Ardour-style scheduler alongside first-class CLAP | Stacking Qt and JUCE |
| **Meadowlark / Firewheel** | Graph compilation as a **pure, testable algorithm in its own crate**. The rule that the transport owns parameter state | A wide MVP, many micro-crates, building our own GUI toolkit |
| **Carla / Bitwig / REAPER** | The bridge pattern (shared memory, a real-time and a non-real-time channel) and grouping by manufacturer | A sandbox as the *default* path at low buffer sizes (§4.4) |

## 3. Proposed architecture

### 3.1 Crates

There are deliberately few crates (Meadowlark lesson). Each boundary below is one we want to test in isolation.

```
riddim/                     workspace
├─ riddim-time      pure    Superclock and beat time, tempo/meter map, conversions. No deps
├─ riddim-model     pure    Engine model types, Op + inverse, validation, serde, schema version
├─ riddim-graph     pure    Model → render plan: topology sort, PDC, buffer assignment, parallel
│                           schedule. Property-tested; never touches devices or plugins
├─ riddim-rt        rt      SPSC queues, deferred drop, param smoothing, RT-safety guards
├─ riddim-plugin    mixed   Format-agnostic PluginInstance trait, scanner protocol, state blobs
│  ├─ format/au             AUv2 and AUv3 via objc2-audio-toolbox / avf-audio / core-audio-kit
│  ├─ format/vst3           via the `vst3` crate (MIT/Apache bindings)
│  ├─ format/clap           via clack-host (after v1)
│  └─ bridge                Out-of-process proxy that implements the same trait (after v1)
├─ riddim-io        rt      CoreAudio HAL device and IO proc, CoreMIDI, audio workgroups
├─ riddim-disk      non-rt  Read-ahead streaming, capture writer, file formats
├─ riddim-engine    mixed   Ties it all together: control side, audio side, transport, render
├─ riddim           api     The public Rust API: commands, queries, events
├─ riddim-ffi       api     C ABI and cbindgen header for Swift and other languages
└─ riddim-cli       tool    Headless: scan, load, play a MIDI file, render, state round-trip
   (riddim-scan)            The scanner child-process binary
```

Formats are modules inside `riddim-plugin` rather than separate crates until they need different dependency or licence treatment (§6).

### 3.2 Threads

| Thread | Real-time? | Does | Must never |
|---|---|---|---|
| **Audio** (CoreAudio IO proc) | yes | Drains commands, runs the render plan, writes capture data to rings, publishes meters | Allocate, free, lock, do I/O, log, or call Obj-C paths that may allocate |
| **Workers** (N = cores − 1, joined to the device's [audio workgroup](https://developer.apple.com/documentation/audiotoolbox/understanding-audio-workgroups)) | yes | Process ready nodes in parallel | Same as Audio |
| **Control** (engine-owned) | no | Applies ops to the model, compiles plans (`riddim-graph`), publishes them, reclaims old ones, owns plugin lifetimes | Block on the audio thread |
| **Main** (the app's macOS main thread) | no | Plugin editors and windows, VST3 `IEditController` calls, AU view controllers | Run long plugin loads (they go async) |
| **Disk** (Butler-style) | no | Read-ahead for playback, flushing capture to files | Ever be waited on by the audio thread |
| **Loader** | no | Async plugin instantiation and state restore; a Superior Drummer preset can be 3.7–18 GB ([Toontrack](https://www.toontrack.com/faq/how-much-ram-does-a-superior-library-or-sdx-use/)) | Block UI or audio |
| **Scanner** (child *process*) | no | Probes plugins, returns descriptions, dies alone if a plugin crashes | — |

**The main-thread rule is a hard constraint, not a choice.** VST3 requires edit-controller calls on the UI thread. AppKit views must be created and touched there too. So `riddim` exposes a `MainThread` handle that Whiplash drives from its run loop. Some plugins also misbehave if instantiated off the main thread. We find out per plugin in phase 1, so loader policy is per format and per plugin **[inferred, to be measured]**.

### 3.3 Data flow

```
 Whiplash ──ops──▶ Control: validate → apply to Model (Arc snapshot) → inverse ops back to app
                          │
                          └─▶ riddim-graph::compile(model, latencies) → RenderPlan
                                   │  (SPSC "swap plan" message)
                                   ▼
 CoreAudio IO proc ─▶ Audio: drain cmd ring → swap plan if one is pending → run plan (+ workers)
                          │     │                       │
                          │     └─ old plan ──SPSC──▶ Control (dropped there, never on Audio)
                          ├─ capture rings ─▶ Disk thread ─▶ files (incremental, flushed)
                          ├─ meters/position ─▶ atomics / triple buffers ─▶ events to app
                          └─ plugin param changes and latency changes ─▶ events to Control/app
```

Key decisions:
- **Stable node identity across recompiles.** Plugin instances, delay-line contents and meter state live in a slot map keyed by stable IDs, which the plan only references. Editing a clip or adding a send recompiles the *plan*, not the plugins. That fixes Tracktion's rebuild-everything pattern while keeping its "the plan is immutable" safety.
- **Parameter changes and transport commands are timestamped**, and are applied sample-accurately inside the block. Automation is evaluated per block from the model's curves, with smoothing. The transport and automation own parameter state, and a live UI gesture overrides automation in touch or latch mode (the Firewheel point).
- **Time:**
  - All time is integer. Ardour's model is the reference: a rate-independent **superclock** for audio time and integer beat ticks for musical time (`temporal/temporal/superclock.h`, `beats.h`). The audio thread works in `i64` samples at the session rate.
  - The tempo map is an immutable snapshot (RCU-style), read once per block.
  - There is no floating-point time accumulation anywhere.
- **Determinism:**
  - Offline render uses a fixed block size and the same plan.
  - **Summing happens in a fixed order regardless of which worker finishes first**, because float addition isn't associative.
  - There are no wall-clock or random inputs.
  - So the same project bounces bit-identically, except where a plugin is itself non-deterministic. That's testable in CI with our own test nodes.
- **Buffer sizes:** 32–2048 frames, changeable at runtime. A change rebuilds the plan and tells plugins, without reopening the project.
- **PDC:** every node reports latency. `compile` inserts delays where paths join (sums, sends, master) and offsets automation and capture placement. A plugin latency change becomes an event, triggers a recompile, and the change is crossfaded **[inferred UX]**. Monitoring paths report their own latency, so Whiplash can offer low-latency monitoring.

### 3.4 Real-time safety, enforced rather than hoped for

- `#[rt]` marked code paths run under `assert_no_alloc` in debug builds, and the whole test suite runs under rtsan in CI.
- The audio side receives only pre-allocated messages. Anything variable-sized (a new plan, new clip data) is built on Control and handed over as an owned pointer, then handed back for dropping.
- Denormals are flushed (FTZ/DAZ) on the audio and worker threads.
- Stress tests run at a 64-sample buffer: graph churn while playing, 30+ test plugins, disk-starvation injection.

| **Editor windows** | `objc2-app-kit` plus `raw-window-handle` 0.6. Working examples: clack's cpal host example (CLAP editor in a winit window), vst3-host's `EmbeddedEditor` | **Write**: an NSWindow/NSView host with resize negotiation and main-thread discipline |
| **Scanner** | Patterns in JUCE (dead-man's pedal), Tracktion (child process), Ardour (separate scanner binaries) | **Write**: `riddim-scan`, a cache keyed by path, version and mtime, and a blocklist |

**We write the hosting layer ourselves on raw bindings**, about four bodies of code: the VST3 host, the AU host, editor windows and the scanner. That's the real cost of going Rust-first. Nobody has a mature, RT-audited Rust host layer for us to adopt.

### 4.3 The `PluginInstance` contract

One format-agnostic trait, so the graph, the model and a future bridge never see format details:
- **Identity and description:** format, id, vendor, version, buses.
- **Lifecycle:** `activate(rate, max_block)`, `process(&mut ProcessContext)` (audio buses, a sample-timestamped event list in and out, transport info), `deactivate`.
- **Parameters:** enumerate, get and set, normalised plus display text, and gestures from the editor.
- **State:** `save() -> Blob`, `restore(Blob)`. Opaque and versioned with the plugin identity: VST3 component plus controller state, or the AU `ClassInfo` plist. A missing plugin keeps its blob and appears as an offline placeholder.
- **Latency and tail**, plus change notifications.
- **Editor:** `open(parent) / close / resize`, main thread only.

### 4.4 Out-of-process hosting

- **AUv3 runs out of process by default**, for free ([Apple](https://developer.apple.com/documentation/audiotoolbox/migrating-your-audio-unit-host-to-the-auv3-api)). AUv2 and VST3 run in process unless we bridge them.
- **The costs are real:**
  - **Ardour's numbers:** about 30 µs per context switch and 256–768 switches per block in a large session, so 7.7–23 ms per cycle against a 1.3 ms budget at 64 samples ([ardour.org](https://ardour.org/plugins-in-process.html)).
  - **The cost is per process and per block**, so a synchronous bridge adds none of the buffer's latency but eats CPU headroom, and a pipelined one adds a block of latency.
  - **REAPER needed a fix for latency drift on bridged AUs** ([KVR thread](https://www.kvraudio.com/forum/viewtopic.php?p=5147973)).
- **Precedents:**
  - Bitwig has five modes: within the engine, together (the default), by manufacturer, by plugin, individually ([Bitwig](https://bitwig.com/userguide/latest/vst_plug-in_handling_and_options)).
  - REAPER has shared and dedicated bridge processes ([reaper.blog](https://reaper.blog/2012/02/run-plugin-as-dedicated-process/)).
  - Carla's shared-memory design is in §2.2.
- **Plan:**
  - **v1 is in process**, with crash *survival* through incremental capture and model autosave (Whiplash's side).
  - **The bridge is a post-v1 `PluginInstance` implementation**: a shared-memory audio and event pool, a semaphore pair per block, separate real-time and non-real-time channels, grouping by manufacturer (Bitwig's middle ground). It is opt-in per plugin.
  - Because the trait is the boundary, adding the bridge later costs nothing upfront except discipline: the real-time path must not assume a plugin pointer is local.
  - A bridged plugin's editor would be a window owned by the child process, not an embedded view. Cross-process NSView embedding isn't a public API **[inferred]**.
- **The honest limit of Rust's safety:** Kontakt is C++ loaded into our address space. Rust protects our code, not theirs. Isolation is the only protection against a plugin crash, and it's paid for in CPU.

### 4.5 Phase 1 spike: "Noire plays, saves and comes back"

A `riddim-cli` and minimal-window tool, not an engine yet.
1. Open CoreAudio output at 48 kHz / 128 frames on Phil's Mac.
2. Scan with `riddim-scan` and list Kontakt 8 Player (VST3 and AU).
3. Instantiate Kontakt **VST3**, open its editor in an NSWindow, and load Noire by hand.
4. Play notes from a MIDI keyboard through CoreMIDI, and from a test sequence.
5. Save the state blob to a file and quit. Relaunch, restore and reopen the editor.
6. Repeat steps 3–5 for Kontakt **AU** (AUv2).

**VST3 first:** the bindings are pure Rust with full interface coverage, the MIT SDK ships a validator and an editor host to diff behaviour against, and the code carries over to Windows. **AU in the same phase:** a trait validated against only one format isn't validated.

## 6. Licensing and business model

**The starting position:** we own all the code, so we can dual-license. The plugin-format layer no longer constrains us:
- VST3 is MIT since 3.8 (§4.2). [nih-plug's warning](https://github.com/robbert-vdh/nih-plug) that VST3 forces GPLv3 is about the old SDK and the GPL `vst3-sys`.
- CLAP is MIT.
- AU hosting uses system frameworks. Apple's [AudioUnitSDK](https://github.com/apple/AudioUnitSDK) is Apache-2.0, and is for *building* AUs, so we don't need it.
- AAX (closed, [Avid agreement](https://developer.avid.com/aax/)) would only ever be a commercial-build feature.

### 6.1 Options

| Option | Precedent | For | Against |
|---|---|---|---|
| **(a) Copyleft + commercial + CLA** | JUCE (AGPLv3 + paid tiers, [juce.com](https://juce.com/get-juce/)), Tracktion Engine (GPLv3+ + paid), Qt (LGPL/GPL + commercial) | Proven in exactly this market, and JUCE sets the price anchor. It is OSI open source. Proprietary embedders must buy | A CLA puts off some contributors. Many Rust shops ban copyleft (fewer users, but they're the buyers). GPLv2-only projects can't use it |
| **(b) Permissive (MIT/Apache) + open core** | The Rust default ([API guidelines](https://rust-lang.github.io/api-guidelines/necessities.html)) | The most adoption and no CLA friction | No leverage at all: embedders never need to pay. Premium crates split the API and invite clones. Paid binaries (Ardour's [$1–50/month subscriptions](https://community.ardour.org/subscribe)) don't work for a library, because people build from source |
| **(c) Source-available, converting later** (FSL/BSL) | Sentry [FSL](https://fsl.software/) → Apache/MIT after 2 years; HashiCorp [BSL](https://www.hashicorp.com/blog/hashicorp-adopts-business-source-license) → the OpenTofu fork | Blocks competitors outright | Not open source, so it fails the brief. "Competing use" is vague for an engine (is every DAW a competitor?). Audio developers won't build on it |

### 6.2 Recommendation: (a), as **AGPL-3.0-only + commercial licence + CLA**

- **AGPL vs GPL:**
  - For a desktop-embedded library, AGPL's §13 adds almost nothing over GPLv3. It only applies when users interact over a network with a *modified* version.
  - It does cover the one secondary client that runs on servers: the **headless renderer** (cloud bounce, collaboration).
  - GPLv3 §13 explicitly allows combining with AGPLv3, so GPLv3 community DAWs can still use it.
  - It matches JUCE, so the market already understands "AGPL or buy".
  - Pick **GPL-3.0-only** instead if Phil rules out server-side clients and wants the friendlier label (Q7).
- **"-only", not "-or-later"**, so we control which future versions apply, not the FSF.
- **CLA:** a licence grant, not an assignment, modelled on [Qt's](https://www.qt.io/legal-contribution-agreement-qt). It needs to be in place **before the first outside PR**, because a DCO only covers the open licence ([developercertificate.org](https://developercertificate.org/)).
- **Commercial tiers modelled on JUCE:** free under a revenue threshold, then Indie and Pro. Exact numbers wait until there is something to sell.
- **Keep the moat in the copyleft core.** The plugin-hosting layer is the hardest, most valuable part, so it stays AGPL. Only generic, non-differentiating pieces (for example `riddim-time` or the RT queues) would ever go MIT/Apache to seed the ecosystem.
- **Dependency hygiene from day one:**
  - Run `cargo deny check licenses` in CI ([cargo-deny](https://embarkstudios.github.io/cargo-deny/checks/licenses/cfg.html)), with an allow list of MIT, Apache-2.0, BSD, ISC, Zlib, Unicode, plus MPL-2.0 for unmodified crates (symphonia, audio_thread_priority).
  - Any GPL dependency (vst3-sys, Carla) blocks the commercial build, so it's denied.
- **Whiplash:** as copyright holder, we can ship Whiplash on any terms. That works only if Riddim's copyright and Whiplash's owner line up legally. Riddim sits under `kaminocorp`, Whiplash under `hejijunhao`, so an internal licence may be needed (Q8).
- **Not legal advice.** Counsel should review the CLA, the commercial EULA, and **the GPL/AGPL vs Mac App Store question** (**UNVERIFIED**; it matters only if we ship through the App Store).

## 7. Risks and open questions

### 7.1 Risks, honestly sized

| Risk | Size | Why / mitigation |
|---|---|---|
| **Rust-first delays Whiplash v0** | **High** | Tracktion + JUCE gives Whiplash an edit model, PDC, render and hosting on day one. Riddim has to build all of it. The plugin host layer alone is P1 (§4.2), and everything above it is P2–P4. **Months before Phil records a song** **[estimate]**. The case for paying that is ownership, safety and a licensable asset, and Phil must want those (Q1) |
| **Plugin long tail** | **High** | Each plugin reads AU and VST3 a little differently: bus layouts, threading, resize, latency changes, state quirks. Four named targets is tractable; "any plugin" isn't. Licensed plugins can't run in CI, so Phil's Mac is the compatibility lab. P1 front-loads this |
| **Writing two format hosts on raw bindings** | **Med-High** | No mature Rust host layer exists. `vst3-host` and `rack` are young and single-author. Mitigation: VST3's validator and editor host, the fallback in §5, and Ardour's and JUCE's format code as reading material |
| **In-process crashes in v1** | **Medium** | One bad plugin kills the session. Mitigations: incremental capture, autosave, the bridge in v1.x. Rust doesn't help inside a C++ plugin |
| **Real-time correctness** | **Medium** | Priority inversion, hidden allocation, Obj-C calls on the audio thread. Mitigations: rtsan in CI, `assert_no_alloc`, the stress suite, human review of every `#[rt]` path. Rust helps here, but it doesn't solve allocation or locking by itself |
| **Main-thread coupling to the app** | **Medium** | Plugin editors and VST3 controllers need the app's main thread, so the engine can't be fully self-contained. The `MainThread` handle has to be designed with Whiplash's UI stack (Q2) |
| **Offline render with streaming samplers** | **Medium** | Kontakt and SD3 stream from disk, and none of the vendors document how they behave in offline render (**UNVERIFIED**). We keep a real-time bounce fallback |
| **Scope creep and burnout** | **Medium** | The Meadowlark lesson. One client, four plugins, crisp exit criteria, no UI work in this repo |
| **Licensing execution** | **Low-Med** | A CLA missing before the first outside PR, or one GPL dependency slipping in, breaks the commercial option. cargo-deny plus a CLA bot from day one |
| **Platform churn** | **Low** | Apple steers hosts towards AUv3, and Rosetta narrows after macOS 27. We target arm64 plugins only, and keep AUv2 and AUv3 behind one trait |
