## Phase 1

**D10. Hosting is tested against free plugins, not the four commercial targets.** Phil has not bought Kontakt/Noire, Superior Drummer 3, EZbass or Helix Native yet (his note of 2026-11-21). Phase 1 is therefore exercised against Riddim's own fixture plugins, Surge XT 1.3.4, and Apple's built-in Audio Units. The four commercial plugins become a later verification target on Phil's Mac; nothing in this repository claims they work.

**D11. Development happens on Linux; macOS code is type-checked from Linux.** The build machine is Linux, so everything platform-neutral is built and tested there. macOS-only code (CoreAudio, CoreMIDI, Audio Units, editor windows, CFBundle loading) compiles behind `cfg(target_os = "macos")`, and `scripts/ci.sh` lints the whole workspace for `aarch64-apple-darwin` before every push. That proves it type-checks, not that it works: every such module is marked "unverified on macOS" in its own documentation until a Mac has run it.

**D12. CI is one small Linux job; everything else runs locally.** GitHub Actions minutes are a hard budget (Phil's note of 2026-11-21). The only workflow, `.github/workflows/ci.yml`, runs `cargo fmt --check`, `cargo clippy` and `cargo test` in one Ubuntu job, only for pull requests that are ready for review, never for drafts, never for changes that touch only `docs/` or Markdown, and a newer push cancels the run before it. There are no macOS or Windows runners, no scheduled runs and no runs on `main`. The rest of the checks (the Apple Silicon type-check of macOS-only code, RealtimeSanitizer, the Surge XT run, `cargo-deny`) are in `scripts/ci.sh` and are run on the build machine before each push; their results are recorded in each phase's notes. An earlier version of this branch had more jobs and a label-triggered macOS workflow; both are gone.

**D13. Pull requests are stacked.** No pull request is merged by the implementer, and each phase builds on the one before, so each phase's pull request is based on the previous phase's branch (phase 1 on `docs/vision`). Merge them in order. Once `docs/vision` reaches `main`, GitHub retargets the next one automatically if branches are deleted on merge; otherwise retarget by hand.

**D14. Crates live under `crates/`, test fixtures under `fixtures/`.** The crate set is the vision's (§3.1). Fixtures (test plugins, test support) are separate packages so they never ship.

**D15. `riddim-scan` is a binary of the `riddim-plugin` crate**, not of `riddim-cli` as the vision's tree sketched. The scanner is the other half of the scan protocol defined in `riddim-plugin`, and keeping them together lets that crate's tests run the real child process. The executable name and behaviour are as the vision describes.

**D16. A plugin is two objects: `PluginInstance` (control side) and `PluginProcessor` (audio side).** The vision lists one contract (§4.3). In Rust the part that crosses to the audio thread has to be a separate, `Send` value, so `activate` returns the processor and `deactivate` takes it back. The instance is deliberately not `Send`: it stays on the thread that created it, which must be the main thread when an editor will be opened.

**D17. Our own allocation guard instead of the `assert_no_alloc` crate.** `riddim_rt::guard` counts heap operations inside real-time sections (per thread and in total) rather than aborting, so a test can run a scenario and assert the count is zero, and tools can print it. Same idea as `assert_no_alloc`, about 100 lines, no dependency. It detects allocation and free only; locks and system calls are for the RealtimeSanitizer job planned in phase 2.

**D18. VST3 host choices.**
- Inactive buses are given real memory (shared silence for inputs, a shared scratch buffer for outputs) rather than null pointers. Plugins differ on whether they check activation before touching a bus.
- A main bus in first position is always active; every other bus starts as the plugin's "default active" flag says. (Found with Surge XT, whose first input bus is a sidechain.)
- MIDI controllers, pitch bend, aftertouch and program change reach the plugin as parameter changes through `IMidiMapping`, which is how VST3 defines it. Controllers the plugin has not mapped are dropped.
- Editor resize requests are queued and answered on the next poll rather than inside the plugin's `resizeView` call. The spec allows either; this avoids re-entrancy. To be revisited if a plugin misbehaves.
- Plugin class ids are written as 32 hex digits in Steinberg's platform-independent order, so a project means the same plugin on macOS and Windows.
- Modules are never unloaded once loaded.

**D19. Audio Unit host choices.**
- One host on the AudioToolbox C API serves version 2 units natively and version 3 units through Apple's bridge. A version 3 unit's own view controller is not requested yet; such units get Apple's generic parameter view. None of the plugins on the target list is version 3.
- State is the unit's `ClassInfo` property list serialised as XML, not binary, because the XML writer orders dictionary keys and the phase 1 exit bar compares blobs byte for byte.
- Parameters are normalised linearly between the unit's minimum and maximum.
- Notifications from the unit arrive through an `AUEventListener` on the instance's run loop, and `poll_events` gives that run loop a turn so hosts without an application event loop still receive them.

**D20. CoreAudio: one device, one IOProc.** A single device is opened for output, optionally capturing from the same device (which is the duplex case for an audio interface). Using *different* input and output devices, such as a MacBook's built-in microphone and speakers, needs an aggregate device; that is not built yet (see D37).

**D21. The toolchain is pinned** to Rust 1.100.0 in `rust-toolchain.toml`, so CI and every machine build with the same compiler and lints.

**D22. The phase 1 player is a throwaway.** `riddim play` drives one plugin straight to the device from code in `riddim-cli`. It is the vision's "tool, not an engine yet" (§4.5) and is replaced by the engine in phase 2.

**D23. CI could not run at all when this was written; checks are run locally and recorded.** On 2026-11-21 GitHub refused to start any Actions job on this repository ("recent account payments have failed or your spending limit needs to be increased"), which is an account matter only Phil can resolve. Every push is checked with `scripts/ci.sh`, which runs what the workflow runs and more (D12), and each phase's notes record the result. When jobs can start again, re-running the checks on the open pull requests is all that is needed.

## Phase 2

**D24. Time is integer, in two clocks.** Audio time is the *superclock*: 282,240,000 units per second (Ardour's constant), which every common sample rate divides, so sample positions convert exactly. Musical time is *ticks*: 3,628,800 per quarter note (10!), fine enough to address single samples at any tempo of 4 bpm or more up to 192 kHz, and divisible by the usual MIDI resolutions and tuplets. A tempo is stored as the exact superclock length of a beat, not as a bpm float. Tempos are constant between points: **there are no tempo ramps yet.**

**D25. Timeline positions carry their clock.** A clip starts at `Position::Beats(ticks)` or `Position::Time(superclock)`. MIDI clips are beat-anchored and move with tempo changes; recorded audio is time-anchored and does not. This is the vision's "superclock for audio time, beat ticks for musical time" applied to clip placement.

**D26. Model conventions.**
- Ids are chosen by the client, checked for uniqueness by the engine. `Model::fresh_id` suggests one.
- The master track always exists, with id 0, and cannot be removed or re-routed.
- Every strip is stereo internally; mono material is spread to both channels.
- Clips within a track and media within the project are kept sorted by id, so a model's contents do not depend on the order edits were made in (which is what lets "apply, inverse, apply" be compared for exact equality).
- Opaque plugin state is base64 inside the JSON form.
- Replacing the whole model (`Engine::load`, opening a project) is not an op and has no inverse.

**D27. Every output port gets its own buffer.** The graph compiler does not reuse buffers between steps. That costs a few megabytes on a large session and buys two things: no aliasing bugs, and steps without a dependency between them can run in parallel (phase 4) with no further analysis. Sources into a port are summed in a fixed order (by upstream node, then port), which is what makes mixes reproducible bit for bit.

**D28. Node state is shared by reference, not held in a slot map.** The vision describes plugin instances, delay lines and meters living "in a slot map keyed by stable IDs, which the plan only references". The implementation keeps the idea and changes the mechanism: each node's persistent state is a reference-counted cell keyed by what the node *is* (`Source(track)`, `Plugin(track, slot)`, `Strip(track)`, ...). The control thread holds one reference; every plan that includes the node holds another. A recompile builds a new plan that points at the same cells. A plugin is unloaded once the last plan that used it has come back from the audio thread. No audio-thread table to size or grow.

**D29. Media is played from memory, not streamed.** Phase 2 decodes each media file once, converts it to the session rate, and plays clips from RAM. The vision's `riddim-disk` includes read-ahead streaming from disk; that is **not built yet**. It matters for long sessions (an hour of stereo at 48 kHz is about 1.4 GB in memory) and is planned alongside the disk-starvation stress tests. *Resolved in phase 4: see D63.*

**D30. Small file-format code of our own.** WAV/RF64 reading and incremental writing, and a windowed-sinc resampler for import, are written here rather than taken from `hound`, `symphonia` or `rubato`. The vision anticipated the WAV writer; the resampler is the same call (about 100 lines, deterministic, used only at import). Standard MIDI Files use `midly`, as the vision suggested. `symphonia` can be added when formats beyond WAV are needed.

**D31. Where a recording lands.**
- The audio thread, not the control thread, fixes the timeline sample a recording starts at, because only it knows the position exactly. If the transport is already rolling, the start is two blocks ahead of the command.
- Capture begins one round trip (device input latency + device output latency + the plan's plugin latency) after that start, so the first captured frame is the one that was played at the start, and the take's clip begins exactly there.
- MIDI is corrected by the output-side latency only (a MIDI input has no meaningful latency of its own).
- Audio takes are written incrementally and survive a crash. **MIDI takes are not**: they are held in memory until the transport stops, then added to the model and written out as a `.mid` file.
- Device latency is taken as the device reports it. `riddim loopback` measures the truth with a cable.

**D32. Looping is suspended while recording.** Loop recording with takes is phase 4. *Resolved in phase 4: see D58.*

**D33. Live MIDI is applied at the start of the next block.** Message timestamps are captured but not yet used to place events inside the block. This meets phase 1's "within one buffer" and is the same for recording (so recorded MIDI is quantised to the block it arrived in, up to one buffer early or late of where a timestamp would put it).

**D34. The C ABI carries structure as JSON.** Configuration, ops, the model and events cross as JSON strings; transport, parameters and status are plain values. The header is generated by cbindgen, checked in, and a test fails if it is stale. Events are polled, not called back, so the client chooses the thread. The ABI is version 0 and will change.

**D35. RealtimeSanitizer through `rtsan-standalone`.** With the `rtsan` feature and `RTSAN_ENABLE=1`, every real-time section is an RTSan context; `scripts/rtsan.sh` runs the engine, host, I/O and disk tests that way (locally, as part of `scripts/ci.sh`; it is not a CI job, see D12). A self-check re-runs itself with deliberate violations and fails the run if the sanitizer does not stop them, so a green run cannot be a silent no-op. Calls into plugin code are excluded. Known limit: the pre-built runtime (LLVM 20.1.1) does not intercept `clock_nanosleep`, so a `thread::sleep` in a real-time section would go unnoticed.

**D36. Mixer conventions.** Pan is a balance control with unity gain at centre (a default strip is bit-transparent). Solo is solo-in-place: soloing a track keeps the buses it plays through open; soloing a bus keeps the tracks that feed it (made precise for sends in D43). Gain changes ramp over 5 ms. The metronome goes straight to the device output, not through the master strip.

**D37. No aggregate devices yet.** Recording on a Mac needs the input and output on one CoreAudio device (true of any audio interface). Built-in microphone plus built-in speakers will not work until the engine can build a private aggregate device; planned for phase 4 with the rest of the device work. *Written in phase 4, unverified: see D64.*

**D38. Bit-identical checks use deterministic plugins.** Surge XT's default patch renders differently from run to run (free-running oscillator phase), which is the plugin's own behaviour and what the vision allows for. "Save, reopen, hear it identically" is therefore asserted bit for bit with the fixture plugins and audio clips, and by ear for real instruments.

**D39. Plugins always run in real-time mode for now.** `ActivateConfig::mode` is `Realtime` even for `riddim render`. The offline mode arrives with bounce in phase 3. *Resolved in phase 3: see D48.*

**D40. A bypassed plugin is passed by without its delay.** Bypass copies the input to the output with no latency, while the graph still compensates for the plugin's reported latency. A bypassed plugin with latency is therefore misaligned by that amount until this is fixed in phase 3. *Resolved in phase 3: see D47.*

**D41. The CLI's "session" is a stand-in for a project.** `riddim session` saves the engine model as JSON beside a media folder so the whole path (build, record, save, reopen, render) can be run from a terminal before Whiplash exists. It is not a project format.

## Phase 3

**D42. Sends.** A track has any number of sends, each to a bus, with a gain (0 to 4, linear) and a mute. Post-fader is the default: the send taps the strip's output, so it follows the fader, pan, mute and polarity. A pre-fader send taps the signal before the strip, which also means before the mute: a muted track still feeds its pre-fader sends (the usual "mute frees pre-fader sends" behaviour; if Phil wants the other convention it is a one-line change in `model_graph.rs`). Sends are edges like any other for latency compensation, and the model refuses routing that loops through one.

**D43. Solo follows the signal.** With any track soloed, a path from a track to the master is heard if it passes through a soloed track. Soloing a track keeps the buses it plays through and its share of the returns it sends to; soloing a bus keeps what feeds it, on the way into that bus only. So soloing an effect return gives the effect alone, not the dry tracks that send to it, and a stem of a return is the wet signal. It is decided per connection: one from `T` into `X` is open if `T` carries soloed signal or `X` leads to a soloed track. To close a track's own output while a post-fader send from it stays open, tracks with post-fader sends have a switch node (`MainOut`) after the strip. One case is approximate: a bus that both carries a soloed track's signal and feeds another soloed bus lets its unsoloed inputs through to its other destinations too. Mute wins over solo.

**D44. Automation lanes.** A lane belongs to a track and controls one target (fader, pan, a send's gain, a plugin parameter); a track has at most one lane per target. Points are in beats, so automation follows the tempo map with the music. Values are in the control's own units (linear gain, pan −1 to 1, normalised plugin values). A point's shape says how to get to the next one: linear, or hold then step. Before the first point and after the last the lane holds their values. A lane in `off` mode is ignored.

**D45. Fader, pan and send automation is read per sample.** The value at each sample is computed from the lane's own breakpoints, never from the previous block. It is exact at the breakpoints, a step lands on its sample even in the middle of a block, and the result does not depend on the buffer size, which is what keeps bounces identical to playback. While a lane is being read the 5 ms fader smoothing is off: the curve is the smoothing, and a step drawn in a lane is a step. The curve is read where the strip's audio is on the timeline (its position minus the latency ahead of it), not where the playhead is.

**D46. Plugin parameter automation is as accurate as the plugin.** The engine sends a parameter's value at the start of each block in which the curve has moved, and an event at the exact sample of every breakpoint inside the block. Ramps are therefore stepped once per block; breakpoints are sample-accurate if the plugin honours event offsets (the VST3 host passes them as parameter-queue points; the Audio Unit host schedules them, unverified). Up to 256 automated parameters per plugin are tracked.

**D47. A bypassed plugin keeps its latency.** Bypass is done by the engine, not the plugin: the input is passed to the output through a delay equal to the plugin's reported latency, so nothing shifts in time when bypass is toggled and compensation elsewhere does not change. The plugin keeps running while bypassed (so its tails and meters behave), which costs CPU; switching it off entirely is a later optimisation.

**D48. Offline bounce runs in an engine of its own.** `bounce(model, request)` starts a second engine on the manual device, in the plugins' offline process mode, loads the model with its saved plugin state, and renders to a WAV with a fixed block size and no clock. It does not touch the live engine or its plugin instances, so a bounce can run while the session keeps playing, and nothing in it depends on timing; two bounces of the same model are bit-identical whenever the plugins are deterministic. The cost is that every plugin is instantiated a second time (memory, and load time for samplers), and that a plugin's current settings have to be captured into the model first (`capture_plugin_states`). The loop, the metronome and record-arming are switched off for the bounce; the plan's latency is rendered and discarded so the file starts exactly at the requested position; a stem is a bounce with those tracks soloed (D43).

**D49. Automation is written on the control side.** Touch, latch and write passes are recorded by the control thread from the values a control produces: fader, pan and send moves arrive as ordinary edits between `touch(down)` and `touch(up)`; plugin parameters arrive from the plugin's editor with its own begin and end gestures. While a lane is being written the control's live value is heard, not the lane. A pass is committed as one `replace_lane` edit when it ends (release for touch, transport stop for latch and write), so it is one undo step, and what was in the lane before and after the pass is kept exactly. Values closer together than 100 ms are joined as one gesture; a control that sat still and then moved is recorded as a flat line and a step. A pass never spans a jump of the playhead: a loop wrap or a locate ends it and starts another where the playhead lands. Timing is that of the control thread's view of the playhead, so points are placed to within a block, not to the sample.

**D50. Plugins load on the plugin main thread, one at a time.** Formats require instantiation on the main thread. The audio thread and the control thread never wait for it: the track plays without the plugin until it is ready, then the plan is swapped. With the engine's own main thread (the default) the application's UI is not involved at all. With an external main thread (the application pumps it from its UI thread, which Audio Unit and VST3 editors need on macOS), a plugin that takes seconds to instantiate holds the UI for that long; loads are handed out one per pump so the UI gets a turn between plugins (this sentence was written before the code did it; the code was corrected to match, with a test, in the same phase). Taking that off the UI thread needs the out-of-process bridge planned for v1.x. Criterion 4's "or the UI" is met only in the first sense.

**D51. The scan cache.** Scan results are kept in a JSON file (`~/Library/Caches/riddim/plugin-scan.json` on macOS, `$XDG_CACHE_HOME/riddim/` elsewhere, or `$RIDDIM_SCAN_CACHE`), keyed by bundle path and trusted only while the bundle's newest modification time and size are unchanged. A bundle that crashes, hangs or fails its scan is blocklisted with the reason and not probed again until it changes or is taken off the list. Before a bundle is probed the file is saved with a mark naming the probing process; if that process dies mid-scan, the next start finds the mark, sees its owner is gone, and treats the bundle as blocked. A mark from a live process blocks nothing, and saving merges with what another process wrote meanwhile, so two hosts can scan at once. There is no lock file: for a bundle both touched, the later writer wins. Audio Units are listed from the system registry each time and are not cached. *Amended while working on v1.x:* a host writes to the cache only what it changed. As first written, a save merged the file with the process's own copy and, where both had an entry, kept its own. Most of that copy is just what the file said when the process started, and one kind of entry goes bad with age: the mark "being probed by process N". A host that read the file while another was mid-probe would later write that mark back over the other's finished result, and from then on the bundle read as one that had taken its host down. A healthy plugin could be blocklisted by nothing more than two Riddim processes starting close together. Now a cache keeps track of the entries it wrote and the bundles it forgot since it last read or wrote the file, and a save (and the start of a scan) takes the file as it is now and lays only those over it.

**D52. "All four target plugins" is deferred with them.** The phase's first exit criterion is a demo song with Kontakt, Superior Drummer 3, EZbass and Helix Native, bounced, in Whiplash. None of the four has been bought, and Whiplash is not built. The stand-in is a demo song through Surge XT and Surge XT Effects (instrument, effect return fed by a send, fader automation), played, saved, reopened and bounced by the engine's test suite on Linux, and the same thing from the CLI on a Mac in the checklist.

**D53. The C ABI gains `riddim_touch` and `riddim_bounce`.** Sends, lanes and automation modes need nothing new: they are ops and model JSON. `riddim_bounce` takes a model and a request as JSON and blocks; it is a free function, not a method of an engine, because of D48. The ABI is still version 0.

## Phase 4

**D54. Extra plugin outputs go to bus tracks.** A multi-out instrument's outputs beyond the first are routed, per slot, to bus tracks (`SetPluginRouting`), where each gets a fader, inserts and sends like anything else; the main output carries on down the instrument's own track. The plugin's output buses are switched on up to the highest one routed, so a bus's place among the active outputs is its own index. An output that is routed but that the plugin does not have, or will not switch on, is left unconnected rather than refused: a project made with a 16-out sampler still opens with an 8-out one.

**D55. A sidechain is a property of the slot, tapped pre- or post-fader.** The source is a track; the plugin's first auxiliary input bus is switched on and fed from it, aligned with the main input like any other path. (That bus need not come second: Surge XT, an instrument, has no main input and its sidechain is its only one.) A post-fader tap follows the source's fader and mute (and so its solo state); a pre-fader tap does not. The master cannot be a source. Bypassing a plugin passes its main input only.

**D56. A track can play another track's notes.** `EventsFrom` on an instrument track adds the events that come out of the end of another track's plugin chain (a drum sampler's MIDI out, an arpeggiator) to its own. With D54 and D55 this makes three kinds of connection between tracks besides outputs and sends, and the model refuses a loop through any mixture of them. Whether a plugin emits events on the audio thread in time with the audio is up to the plugin; the engine passes them on in the same block, at their sample offsets.

**D57. Changing a plugin's buses means restarting it, and the plugin is out of the mix meanwhile.** Formats only allow buses to change while a plugin is inactive. The engine takes the plugin out of the plan, waits for the audio thread to let go of it, deactivates, reconfigures, activates, and puts it back; the instance survives, so settings do, and parameter changes that arrive in the gap are handed over afterwards. For a block or a few the track plays without the plugin (an instrument is silent, an effect is bypassed without its latency). The same restart serves a buffer-size change and a plugin's own request to be restarted. Plugin instances are named to the plugin host by a serial number, not by slot, so a slot emptied and refilled in quick succession cannot have its new plugin unloaded in place of the old.

**D58. Loop recording keeps one file and makes a clip per time round.** While recording, an active loop keeps wrapping, and each time round is a pass. A track's audio goes to one continuous file; when recording stops, each pass becomes a clip that plays its part of that file, marked as a take (`Clip::take`: a group and a number). The newest take that is at least half as long as the longest is the audible one and the rest are muted; choosing another take is muting and unmuting clips, which needs no engine support. MIDI is the same with a clip per pass; a note held over the wrap ends with its pass. The tail of the last pass that had not come back through the input when the transport stopped is not in the file, as with any recording. The transport cannot be located while recording.

**D59. Punch recording replaces what is on the track, by ordinary edits.** With a punch range enabled, recording is confined to it: the take starts at the punch-in (or where the playhead is, if that is later), the engine captures exactly the range (it waits the round trip after the punch-out for the last of it to come back), recording ends by itself, and the transport plays on. Audio clips already on the track are trimmed back, split around the range or removed to make room, in the same batch of ops as the new clip, so one undo restores the track exactly; no media is altered. MIDI takes are added without clearing anything (overdub). A punch with the playhead already past the range is refused, by the audio thread, which is the one that knows where the playhead is. When both a loop and a punch range are enabled, the punch wins and the loop does not wrap for that recording. Plain recording (no punch) still layers over existing clips as before.

**D60. Parallel rendering is deterministic by construction, and the wake-up is a system call.** Render threads and the audio thread run the same function for each step on the same buffers. The plan compiler already gives every output port its own buffer and fixes the order in which inputs are summed, so a step's result cannot depend on which thread ran it or when, and node messages are delivered in step order afterwards. Scheduling is dependency counting with a ready queue, lock-free and allocation-free. Idle workers spin for a moment and then park; the audio thread unparks them when a block opens, which is a futex wake on Linux and a semaphore signal on macOS. That is the one system call on the audio path, it does not block, and it is excluded from the sanitizer's checks explicitly (it flagged it, correctly). Plans with fewer than 24 steps run on the audio thread alone (`parallel_from`). By default there are no render threads on the deviceless backends and one fewer than the cores (at most 7) on hardware.

**D61. Render threads join the device's audio workgroup (unverified).** On macOS each render thread makes itself a real-time thread with the block as its deadline and joins the workgroup of the device's I/O thread. Written against the documented C interface with a generously sized join token; it type-checks for Apple Silicon and has never run. If joining fails the thread renders as an ordinary one. The deadline is not updated when the buffer size changes.

**D62. A buffer-size change re-opens nothing.** `set_buffer_size` pauses the device, changes its buffer size, and resumes it with the same callback. The engine's own block size follows: new buffers of the new size travel to the audio thread with the next plan and carry their size with them, so the audio thread can never run a block larger than the buffers it holds, and every plugin is restarted (D57) to be told the new maximum. The transport keeps its place; nothing is reloaded. Sizes from 16 to 4096 frames are accepted (the vision asks for 32 to 2048), the device may clamp, and it is refused while recording.

**D63. Long files are played from disk in pages; the manual device waits for them.** A file of the session's sample rate with at least 30 seconds of audio (`StreamingConfig::threshold_frames`) is not decoded into memory. A reader thread keeps the pages (32,768 frames each) within 4 s ahead and 1 s behind the playhead loaded, also from the loop start while a loop is on and around the target of a locate as soon as it is asked for. The audio thread looks a page up with one atomic load; a page that is not there plays as silence and is counted (`playback_starved`). A page that is let go is freed two audio blocks later, since a page pointer is only used within the block that loaded it. On the manual device there is no clock, so a missing page is read on the spot: a bounce never depends on disk speed. Files that need resampling, and short ones, are still decoded whole. There is no streaming resampler.

**D64. One private aggregate device when input and output are separate (unverified).** If capture is asked for and the output device has no inputs, the CoreAudio backend creates a private aggregate device of the output device and the default input device, clocked by the output with drift correction on the input, runs on that, and destroys it with the stream. Type-checks for Apple Silicon; never run. In particular the latency an aggregate reports for its inputs has not been checked against a loopback measurement.

**D65. The event set.** Everything the engine tells its client is one of the events in [`docs/api/events.md`](api/events.md), and every one of them that can be staged without a failing disk or device is produced and checked by one test. Events are delivered in order per subscriber; periodic ones (position, meters, load) come about thirty times a second or once a second and are skipped when nobody subscribes. Plugin latency is now asked of each plugin on every pump as well as when it announces a change, because some announce before their audio side has changed and some never do.

**D66. Record pressed during the last take's wind-down starts a new recording.** Found by the stress run: Stop followed at once by Record lost the Record, because the finished take had not come back from the audio thread yet. The request is now remembered and honoured as soon as the previous take has been put away.

**D67. "Sustained" real-time-safety runs are a script, not CI.** The vision's fourth exit criterion for this phase (rtsan plus the stress suite green in CI for four weeks) cannot be met inside the Actions budget, and four weeks have not passed. What exists: the stress test runs for a few seconds in every test run, `scripts/stress.sh N` runs it for N seconds under RealtimeSanitizer, and `scripts/ci.sh` runs the whole suite under the sanitizer before each push.
