# Phase 4: v1

Completion notes for phase 4 of the vision (the fourth row of §5): multi-out instruments, sidechain, plugin MIDI out, loop and punch recording with takes, the parallel executor, runtime buffer-size changes, the full event API. Also in this phase, because earlier phases put them off until now: playing long files from disk, recording through separate input and output devices, and the stress run.

**Where it stands (2026-11-21):** everything in the phase's scope is written, and everything that can run without a Mac passes on Linux. **Nothing here has run on a Mac or on real audio hardware, and nothing has been run with Kontakt, Superior Drummer 3, EZbass or Helix Native**, which have not been bought. Three of the four exit criteria are about Phil, his Mac, and four weeks of elapsed time, and cannot be met from here; the one that can be (parallel and single-threaded bounces identical) is met.

Still true from earlier phases: GitHub Actions could not start jobs on this repository (an account billing matter), and CI is one small Linux job in any case (decision D12), so the fuller checks are run locally and recorded below.

## What the tests actually establish

All on Linux. Everything except the timer-driven tests runs on a simulated device that advances only when told to, so results are exact and repeatable.

- **A second plugin output plays through its own bus.** Routing it leaves the sum unchanged, to the sample; the two outputs then have a fader each and add up to the whole; undoing switches the output off again. An output the plugin does not have is left unconnected. With Surge XT, "Scene A" is routed to a bus and the plugin comes back from the restart playing.
- **Sidechains arrive where they should.** A pre-fader key reaches the plugin although its source is muted; a post-fader key follows the source's fader and mute; a bypassed plugin passes none of it. Surge XT's sidechain, which is its only input, is found and fed.
- **Notes cross between tracks.** A second instrument fed from the first plays the same notes on the same samples: the sum is exactly double. Note-offs travel too.
- **Restarting a plugin loses nothing.** A knob turned beforehand stays turned; a slot emptied and refilled at once gets a working plugin.
- **Loop recording gives a take per time round.** Four takes through a simulated loopback: each sits where its pass was on the timeline, plays its own part of the one file, and holds exactly what was played over those samples. The newest whole take is audible; the cut-short last one is not. One undo removes them all. MIDI the same, with a note held over the wrap ended at the wrap.
- **Punch recording takes the range and nothing else.** The take starts on the punch-in sample, is exactly the range long, and recording ends by itself with the transport still playing. The clip already on the track is split around it and carries on from the right place in its file; played back, old material, new material, old material; one undo restores the track exactly. A punch that cannot happen is refused.
- **Parallel rendering changes nothing audible, or inaudible.** See criterion 3.
- **The buffer size changes under a running engine.** The same project plays sample for sample identically at 32, 64, 128, 512 and 2048 frames after live changes; a change while playing leaves the timeline where it should be; a timer-driven device carries on through one.
- **Long files play from disk as from memory.** Same samples through locates and fades; about two dozen pages of 98 held while looping, nothing missed; with a 150 ms delay per page the disk falls behind, the engine says so, and the audio callback never pauses.
- **Every stageable event is sent and serialises.** One test, twenty-one kinds.
- **The engine holds up under churn.** See the stress run below.
- **The audio path still does no heap work**, render threads included: asserted in every engine test, and under RealtimeSanitizer.

## Findings

- **The property test found a model that could be made invalid by a tempo change.** A punch range with one end in beats and the other in time can be turned inside out by a later tempo edit. Such a range now does nothing instead of making the project unopenable (the loop range was already treated that way).
- **The stress run found a lost Record.** Stop followed at once by Record dropped the Record, because the finished take had not come back from the audio thread yet (D66).
- **A slot refilled too quickly got its new plugin unloaded.** Present since phase 2 and never hit, because the tests happened to run a block in between. Plugin instances are now named to the host by serial number (D57).
- **Surge XT's sidechain is its first input bus, not its second.** The first version assumed a main input came first. The demo song caught it.
- **A fixture can announce a latency change before it has happened.** The host now asks each plugin its latency on every pump rather than trusting the announcement's timing (D65).
- **`bool::then_some` evaluates its argument.** A page handle that frees its page when dropped was built for the "no page" case too. It crashed at once, in the first streaming test, which is the right time.
- **RealtimeSanitizer flags the worker wake-up**, correctly: it is a system call. It is the one exception on the audio path, and it is written down as one (D60).

## Known gaps

- **Plugins drop out for a moment when restarted** (D57): on a routing change that touches their buses, on a buffer-size change, or when they ask.
- **No streaming resampler** (D63): a long file at another sample rate is still decoded into memory.
- **A locate into a cold part of a streamed file can cost a moment of silence** while playing (bounded in the tests at a quarter of a second; in practice a few blocks).
- **Loop takes share one file** (D58): deleting one take's clip does not free disk space until all are gone.
- **Punch and loop together**: the punch wins and the loop does not wrap (D59).
- **Render threads' deadline is not updated on a buffer-size change** (D61).
- **No notification when devices appear, disappear or the default device changes.**
- **`plugin_editor_resize` is forwarded but untested**: the fixtures have no editor.
- Still open from earlier phases: no tempo ramps, live MIDI at block boundaries, plugin parameter ramps stepped per block, a bounce instantiates plugins a second time.

## Mac verification checklist

For Phil's Mac. Needs Surge XT installed. Steps 5 and 6 need a microphone or interface input. Please paste back the output of anything that fails. The four commercial plugins are step 9, for when they exist; exit criteria 1 and 2 are step 10.

**0. Build and test**

```sh
git checkout feat/p4-v1
cargo build --workspace --release
RIDDIM_TEST_VST3="/Library/Audio/Plug-Ins/VST3/Surge XT.vst3;/Library/Audio/Plug-Ins/VST3/Surge XT Effects.vst3" \
  scripts/ci.sh 2>&1 | tee p4-mac-ci.log
scripts/stress.sh 300 2>&1 | tee p4-mac-stress.log
```

Good: `All checks passed.`, a line starting `demo song: rerouted`, and the stress run ending `test result: ok` with a line starting `stress:`. (This includes every earlier phase's tests. The Audio Unit, editor, CoreAudio, workgroup and aggregate-device code has never run anywhere before this.)

**1. A mix to work with**

```sh
mkdir -p ~/riddim-test && cd ~/riddim-test
R=~/path/to/riddim/target/release/riddim
$R session new v1.json --instrument "Surge XT" --sequence --send-effect "Surge XT Effects" --audio-input 1
```

**2. Render threads and the audio workgroup**

```sh
$R session play v1.json --seconds 20
$R session play v1.json --seconds 20 --render-threads 0
```

Good: both sound the same; `xruns 0` and `audio-thread heap operations 0` on both; `peak dsp load` is a believable percentage. The first run uses the default (one thread fewer than the cores, at most 7), in the device's audio workgroup. If the first run has xruns and the second does not, the workgroup code is the suspect: that output is what I need.

**3. Changing the buffer size while playing**

```sh
$R session play v1.json --seconds 10 --buffer 64 --switch-buffer 512
$R session play v1.json --seconds 10 --buffer 512 --switch-buffer 32
```

Good: `buffer size changed to ... frames while running` three seconds in, a brief dropout as the plugins restart, then playback carries on in time; `xruns` may show a few from the change itself.

**4. Multi-out and sidechain**

```sh
cat > routing.json <<'EOF'
[
  {"op":"set_plugin_routing","track":1,"slot":2,
   "outputs":[{"bus":1,"target":1000}],
   "sidechain":null}
]
EOF
$R session apply v1.json routing.json
$R session info v1.json
$R session play v1.json --seconds 10 --editor
```

Good: `info` shows `output 2 to track 1000` under the Surge XT slot, and it plays as before. (Output 2 is Surge XT's "Scene A" output. Whether Surge XT sends anything there depends on its own output setting, which I have not looked at; what this step checks is that switching a second output on, which means restarting the plugin, works on macOS.) To try the sidechain as well, put `"sidechain":{"source":4,"pre_fader":true}` in place of `null`: track 4 is the audio track.

**5. Loop recording with takes**

```sh
$R session record v1.json --loop 0:8 --seconds 14
$R session info v1.json
$R session play v1.json --seconds 10
```

Play or sing along for three passes of the two-bar loop (8 beats, four seconds a time). Good: `take 1 on track 4`, `take 2 ...`, `take 3 ...`; `info` shows them as takes of track 4 with all but one muted; playback has the unmuted take in time with the arpeggio. On a Mac with no interface this is also the test of the aggregate device (built-in microphone with built-in speakers): the `device:` line should name both.

**6. Punch recording**

```sh
$R session record v1.json --punch 4:8 --seconds 8
$R session info v1.json
```

Good: `recording 1 track(s) from sample 96000` (beat 4 at 120 bpm and 48 kHz), `take on track 4: 96000 frames`, and the earlier take's clip split around beats 4 to 8.

**7. Bounce with and without render threads**

```sh
$R session render v1.json -o one.wav --seconds 16 --threads 0
$R session render v1.json -o eight.wav --seconds 16 --threads 8
cmp one.wav eight.wav
```

Good with deterministic plugins: `cmp` prints nothing. With Surge XT the two differ slightly (it is not deterministic, decision D38); repeat with `--threads 0` twice to see the same.

**8. A long file from disk**

```sh
$R session new long.json --audio-input 1
$R session record long.json --seconds 120
$R session play long.json --seconds 30
```

A take longer than 30 seconds is played from disk rather than from memory. Good: it plays back as recorded, and the summary's `frames of streamed files not read in time` is 0.

**9. The four target plugins**, when they are installed: Kontakt and Superior Drummer 3 with several outputs routed (step 4, more `outputs` entries, with the plugin named as `riddim scan` lists it), Superior Drummer 3's MIDI out into EZbass or another instrument (`{"op":"set_track","id":<track>,"change":{"field":"events_from","value":<source track>}}`), Helix Native with a sidechain. Each is a `session apply` away.

**10. The exit criteria themselves**: the reference session at 64 frames for an hour (`session play --buffer 64 --seconds 3600`, good: `xruns 0`), and a track made from recording to bounce in Whiplash.
